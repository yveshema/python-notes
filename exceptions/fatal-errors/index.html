Exiting on a fatal error

Not every error can be recovered from

Some failures have an obvious fallback. A missing config file? Use defaults. A bad line in a data file? Skip it and count it. A typo at a prompt? Ask again.

Others leave nothing sensible to do:

  • The input file the program exists to process is not there.
  • A required command-line argument was not given.
  • The data file is corrupt in a way that makes every later result meaningless.

For these, stopping is correct. What is not correct is stopping with a traceback, which tells the user about int() and line numbers in your code when the actual message they need is "no such file: sales.csv". A fatal error should produce:

  1. a short message saying what was wrong, on the error stream,
  2. a non-zero exit code, so other programs can tell it failed,
  3. no traceback.

sys.exit — stopping on purpose

import sys

sys.exit()        # quit, reporting success (exit code 0)
sys.exit(0)       # the same, said explicitly
sys.exit(1)       # quit, reporting failure
sys.exit("no input file given")   # print the message to stderr, exit with code 1

By convention — one that every shell, scheduler, and CI system relies on — 0 means success and any non-zero value means failure. 1 is the general-purpose "it failed" code and is all you need; larger numbers are sometimes used to distinguish kinds of failure, which is useful only if you document them.

You can see the code your program returned from the shell:

$ python3 report.py missing.csv
report.py: no such file: missing.csv
$ echo $?
1

That echo $? matters more than it looks. It is how a scheduled task, a shell script, or a pipeline knows whether to carry on, and it is the main reason a script that fails must not exit 0.

exit() and quit() are not for scripts

The bare exit() and quit() you may have seen at the >>> prompt are conveniences added for interactive use. They can be absent when a program runs in other contexts. In a program file, use sys.exit().

Two output streams: stdout and stderr

Every program has two output channels. Normal results go to stdout; errors and diagnostics go to stderr. print uses stdout unless told otherwise:

import sys

print("42 records processed")                      # stdout — the result
print("skipping line 7", file=sys.stderr)          # stderr — the commentary

Keeping them separate is what makes a script usable as part of something larger. The user can save the real output while still seeing the errors on screen:

$ python3 report.py data.csv > report.txt
skipping line 7

The warning appeared on the terminal; only the report went into the file. Had you printed the warning to stdout, it would be sitting in the middle of report.txt, corrupting it.

Rule of thumb: if it is the answer, print it; if it is about the program, send it to stderr.

A small die helper

Message plus exit code is such a common pair that it is worth one function:

import sys

def die(message, code=1):
    """Print `message` to stderr and exit with `code` (non-zero = failure)."""
    print(f"error: {message}", file=sys.stderr)
    sys.exit(code)

if len(sys.argv) < 2:
    die("usage: report.py <datafile>")

Now every fatal path in the program is one readable line, and the formatting of errors is consistent.

sys.exit raises an exception

sys.exit works by raising SystemExit, which is why finally blocks and with statements still run on the way out — files get closed properly. It is also why a bare except: can accidentally catch an attempted exit and prevent it. One more reason to catch specific exceptions.

Deciding at the top of the program

The pieces now assemble into the standard shape for a script: functions raise, and main decides what is fatal.

import sys

def load_scores(path):
    """Return a list of (name, score). Raises FileNotFoundError or ValueError."""
    scores = []
    with open(path) as f:
        for number, line in enumerate(f, 1):
            name, _, raw = line.partition(",")
            try:
                scores.append((name.strip(), int(raw)))
            except ValueError:
                print(f"line {number}: skipping {line.strip()!r}", file=sys.stderr)
    if not scores:
        raise ValueError("no usable rows")
    return scores

def main():
    if len(sys.argv) != 2:
        print("usage: report.py <datafile>", file=sys.stderr)
        sys.exit(1)

    path = sys.argv[1]
    try:
        scores = load_scores(path)
    except FileNotFoundError:
        print(f"error: no such file: {path}", file=sys.stderr)
        sys.exit(1)
    except PermissionError:
        print(f"error: cannot read {path}", file=sys.stderr)
        sys.exit(1)
    except ValueError as e:
        print(f"error: {path}: {e}", file=sys.stderr)
        sys.exit(1)

    for name, score in sorted(scores, key=lambda pair: pair[1], reverse=True):
        print(f"{name:20} {score:3}")

if __name__ == "__main__":
    main()

Three things to notice:

  • load_scores contains no sys.exit. It handles what it can (a bad row) and raises what it cannot (an empty result). It stays callable from a test.
  • main contains every exit. One place in the program decides to stop, which means you can see all the ways it can fail by reading one function.
  • Bad rows go to stderr and the program continues; a missing file ends it. That distinction — recoverable or fatal — is a design decision, and it is made explicitly here rather than by accident.

Handling Ctrl-C

When a user presses Ctrl-C, Python raises KeyboardInterrupt. Left alone it prints a traceback, which looks like a crash for what was a deliberate act. If your program runs long enough for anyone to interrupt it, say goodbye properly:

if __name__ == "__main__":
    try:
        main()
    except KeyboardInterrupt:
        print("\ninterrupted", file=sys.stderr)
        sys.exit(130)            # the conventional code for "killed by Ctrl-C"

The \n moves past the ^C the terminal echoed. Code 130 is the shell convention; 1 is acceptable if you prefer not to explain the number.

Cleanup on the way out

If the program holds something that must be tidied — a half-written output file, a temporary directory — put the cleanup in a finally so it happens whether the program ended normally, crashed, or was interrupted.

The one acceptable broad handler

Everything so far has insisted on catching specific exceptions. There is a single exception to that rule: a last-resort handler at the very top of a program, whose job is to turn an unanticipated crash into a readable message while still failing.

if __name__ == "__main__":
    try:
        main()
    except KeyboardInterrupt:
        print("\ninterrupted", file=sys.stderr)
        sys.exit(130)
    except Exception as e:                       # last resort only
        print(f"unexpected error: {type(e).__name__}: {e}", file=sys.stderr)
        sys.exit(1)

This is legitimate because it does not pretend the error did not happen: it names the exception type, prints the message, and exits non-zero. It is still a trade — you have given up the traceback that would have told you where — so while you are developing, leave it out. Add it when the program is finished and being used by someone who should not have to read Python internals.

What this must never become

except Exception:
    pass                     # or: print("something went wrong")

A handler that discards the error and carries on, or exits 0, converts a loud failure into wrong results that nobody notices. That is strictly worse than crashing.

Summary of the exit decision

Situation Response
Bad value typed at a prompt Re-prompt (loop)
Optional file missing Use a default, mention it on stderr
One bad row in a data file Skip it, count it, report on stderr
Required argument missing Usage message on stderr, sys.exit(1)
Required input file missing or unreadable Message on stderr, sys.exit(1)
Output cannot be written Message on stderr, sys.exit(1)
Ctrl-C Short message, sys.exit(130)
A bug in your own code Let it crash — you need the traceback
