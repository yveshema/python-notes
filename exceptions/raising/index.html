Raising exceptions

Why a function should raise

So far exceptions have been something that happens to your code. They are also something your code can do deliberately. When a function is asked to do something it cannot do sensibly, raising an exception is how it says so.

Consider a function that should never receive a negative number:

def square_root(n):
    return n ** 0.5

>>> square_root(-9)
(1.8369701987210297e-16+3j)

That is a complex number, which is almost certainly not what the caller wanted, and nothing in the program will notice. Three responses are possible, and only one of them is good.

def square_root(n):
    if n < 0:
        print("negative!")       # 1. print and carry on
        return None

Printing is a dead end: the caller gets None and crashes later somewhere unrelated, and the message appears even if the caller was perfectly happy to handle the problem itself.

def square_root(n):
    if n < 0:
        return None              # 2. return a sentinel value
    return n ** 0.5

Returning None is better, but now every caller must remember to check, and a caller who forgets gets TypeError: unsupported operand type(s) several lines later, pointing at innocent code.

def square_root(n):
    if n < 0:                    # 3. raise — the right answer
        raise ValueError(f"cannot take the square root of {n}")
    return n ** 0.5

Now the problem is reported at the exact moment and place it occurred, it cannot be ignored by accident, and a caller who does want to handle it can:

try:
    print(square_root(value))
except ValueError as e:
    print(f"skipping: {e}")

The raise statement

The syntax is raise followed by the exception type and a message in parentheses:

raise ValueError("amount must be positive")
raise KeyError("no such user")
raise FileNotFoundError("config.txt not found")

Like return, raise ends the function immediately — nothing after it in that function runs. Unlike return, it does not hand a value back; it starts the search for a handler described earlier in this lesson.

The message is for a human reading a traceback or a log, so make it useful:

# unhelpful
raise ValueError("bad input")

# helpful — says what was wrong, and with what value
raise ValueError(f"age must be between 0 and 120, got {age}")

Use !r for values that came from text

f"got {value!r}" shows the value the way Python would write it, so "42 " prints as '42 ' and you can see the stray space. Without !r it prints as 42 and looks fine. For anything derived from user input or a file, !r is the better default.

Choosing which exception to raise

Pick the built-in whose meaning matches your problem. The caller catches by type, so the type is part of your function's contract.

Situation Raise
A value is the right type but out of range or malformed ValueError
The argument is the wrong type entirely TypeError
A requested key or name does not exist KeyError
An index is out of range IndexError
A required file is missing FileNotFoundError
The operation is fine but the program is in the wrong state for it RuntimeError
A function exists but you have not written it yet NotImplementedError

ValueError covers the large majority of argument problems in beginner code. When in doubt between ValueError and TypeError, ask: would a different value of the same type have worked? If yes, it is a ValueError.

def withdraw(balance, amount):
    if not isinstance(amount, (int, float)):
        raise TypeError(f"amount must be a number, got {type(amount).__name__}")
    if amount <= 0:
        raise ValueError(f"amount must be positive, got {amount}")
    if amount > balance:
        raise ValueError(f"cannot withdraw {amount} from a balance of {balance}")
    return balance - amount

Why no custom exceptions here

Large programs define their own exception types (class ConfigError(Exception): ...) so callers can catch their failures specifically. That needs classes, which are out of scope for this course — and for scripts of the size you are writing, the built-ins are genuinely sufficient. The habit that transfers is choosing the type deliberately rather than defaulting to one.

assert is not for argument checking

assert looks like a validation tool and is not one:

def withdraw(balance, amount):
    assert amount > 0, "amount must be positive"       # DON'T do this

Two reasons to avoid it here:

  1. Assertions can be switched off. Running python3 -O script.py removes every assert statement, and your validation silently disappears.
  2. It raises the wrong thing. AssertionError tells the caller "a programmer assumption broke", not "your argument was invalid".

Use assert for tests — stating what your own code should produce, as in assert to_celsius(212) == 100. Use raise for input that comes from outside your code.

Re-raising: handle part of a problem, pass the rest on

Sometimes a function can do something useful about a failure — log it, clean up — but cannot decide what the program should do next. Catch it, do your part, then raise with no arguments to send the same exception onward:

def load_settings(path):      # assumes `import sys` at the top of the file
    try:
        with open(path) as f:
            return parse(f.read())
    except FileNotFoundError:
        print(f"settings file {path!r} is missing", file=sys.stderr)
        raise                    # same exception continues up to the caller

A bare raise inside an except block re-raises whatever was caught, keeping the original traceback intact. This is much better than raise FileNotFoundError(...), which would throw away the information about where the problem started.

Translating an exception into a clearer one

Other times the exception you caught is technically accurate but unhelpful to your caller. Raise a different one with a better message, and use from e so the original is still recorded:

def read_port(path):
    """Return the port number stored in a one-line file."""
    try:
        with open(path) as f:
            return int(f.read().strip())
    except ValueError as e:
        raise ValueError(f"{path} must contain a port number") from e

The traceback then shows both: your message, and below it "The above exception was the direct cause of the following exception" with the original. You get a readable error without losing the detail.

Don't translate just to say less

Replacing a precise built-in message with a vague one of your own is a step backwards. Translate only when you can add information the original lacked — which file, which field, which line number.

Who raises and who catches

The division of labour that keeps programs readable:

  • Raise low, catch high. Small functions that compute and convert should raise and not handle. The top of the program — the input loop, main() — handles.
  • A function should not catch an exception it cannot do anything about. If the only honest response is "tell someone", let it propagate; the caller is better placed.
  • Never swallow silently. except ValueError: pass throws away information. If the value really is skippable, say so in a comment or a message.
import sys

# parse_line raises; the loop decides to skip bad lines and report them
def parse_line(line):
    name, score = line.split(",")
    return name.strip(), int(score)

def load(path):
    records, bad = [], 0
    with open(path) as f:
        for number, line in enumerate(f, 1):
            try:
                records.append(parse_line(line))
            except ValueError:
                bad += 1
                print(f"line {number}: skipping {line.strip()!r}", file=sys.stderr)
    return records, bad

parse_line stays short and testable because it has no error handling at all. load is the layer that knows "one bad line should not kill the import", so the handler lives there. That separation is the whole point of letting exceptions travel.
