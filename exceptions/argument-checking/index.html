Checking arguments

The question this page answers

You write a function. Someone — possibly you, next week — calls it with something unexpected: a negative number, an empty list, the string "12 " instead of 12, None. How much should the function check, and what should it do when a check fails?

There is no single answer, but there are four recognisable strategies, and choosing between them deliberately is most of the skill.

Strategy 1 — don't check, and document the contract

The default, and the right choice more often than beginners expect:

def average(values):
    """Return the mean of a non-empty list of numbers."""
    return sum(values) / len(values)

No validation at all. If values is empty you get ZeroDivisionError; if it contains strings you get TypeError. In both cases Python's own message names the problem, and the traceback points at this function.

This is appropriate when:

  • The function is an internal helper called only by your own code.
  • Python's own error is already clear enough.
  • The caller has already validated — checking again is noise.

What makes it legitimate is the docstring. "A non-empty list of numbers" states the contract, so a caller who violates it has been told. Validation you skip is only acceptable if the requirement is written down.

This strategy fails when the error surfaces far away

average([]) crashing inside average is fine. A function that quietly returns None on bad input, and crashes three function calls later, is not — see the sentinel-value problem discussed earlier in this lesson.

Strategy 2 — check first, then raise (guard clauses)

Validate at the top of the function and raise immediately if something is wrong. The checks come before any real work, so the function either fails on line 2 or runs to completion:

def average(values):
    """Return the mean of a list of numbers.

    Raises:
        ValueError: if `values` is empty.
    """
    if not values:
        raise ValueError("average() needs at least one value")
    return sum(values) / len(values)

These leading if ... raise lines are called guard clauses. The pattern scales to several conditions, each with its own message:

def book_room(nights, guests, capacity):
    if nights < 1:
        raise ValueError(f"nights must be at least 1, got {nights}")
    if guests < 1:
        raise ValueError(f"guests must be at least 1, got {guests}")
    if guests > capacity:
        raise ValueError(f"{guests} guests exceeds capacity of {capacity}")
    return nights * guests * 50

Three properties make this readable: every check is one line, every message names the offending value, and the actual work sits at the end with no nesting. Compare the same logic written with if/else:

def book_room(nights, guests, capacity):      # harder to follow
    if nights >= 1:
        if guests >= 1:
            if guests <= capacity:
                return nights * guests * 50
            else:
                ...

Guard clauses exist to avoid exactly that staircase.

Use this strategy when the function is a boundary: called with data from a user, a file, a command line, or another part of the system you do not control.

Strategy 3 — try the operation and handle the failure

Rather than inspecting a value to predict whether an operation will work, attempt the operation and catch the failure. Python's conversion and lookup functions are already precise about what they reject, so this is often both shorter and more correct:

# checking first — long, and never quite complete
def to_number(text):
    if text.isdigit():               # rejects "-5", "3.5", " 7 "
        return int(text)
    return None

# attempting — handles every case int() handles, which is the real question
def to_number(text):
    try:
        return int(text)
    except ValueError:
        raise ValueError(f"not a whole number: {text!r}") from None

The two approaches have names worth knowing, because you will see them in other people's code and documentation:

  • Look before you leap — check the condition, then act (strategy 2).
  • Ask forgiveness, not permission — act, and handle the failure (strategy 3).

Python leans towards the second, and for file operations it is not merely a preference:

# a real bug — the file can disappear between the check and the open
if path.exists():
    with open(path) as f:
        data = f.read()

# correct — the only moment that matters is the moment you open it
try:
    with open(path) as f:
        data = f.read()
except FileNotFoundError:
    data = ""

Any check of the filesystem is out of date the instant it returns. The open itself is the only reliable test.

from None suppresses the original exception

In the to_number example above, from None hides the internal invalid literal for int() message so the traceback shows only yours. Use it when your message is strictly more informative; use from e when the original detail still helps.

Strategy 4 — normalise before you validate

Much "bad" input is merely untidy. Before rejecting a value, clean it:

def parse_answer(text):
    """Return True/False for a yes/no answer, raising ValueError otherwise."""
    answer = text.strip().lower()            # normalise first
    if answer in ("y", "yes", "true", "1"):
        return True
    if answer in ("n", "no", "false", "0"):
        return False
    raise ValueError(f"expected yes or no, got {text!r}")

" YES\n" is an acceptable answer typed by a real person; treating it as an error would be hostile. Strip whitespace, fold case, and convert types at the edge of your program, so everything inside works with clean values.

Choosing a strategy

If the function… Use
is an internal helper you call yourself 1 — document, don't check
receives user input, file data, or sys.argv 2 — guard clauses that raise
converts text to a number or looks something up 3 — try and handle
accepts human-typed text 4 — normalise, then 2 or 3

These combine. A realistic boundary function normalises, tries the conversion, and guards the range:

def parse_percentage(text):
    """Return an int 0-100 parsed from `text`."""
    try:
        value = int(text.strip())
    except ValueError:
        raise ValueError(f"not a whole number: {text!r}") from None
    if not 0 <= value <= 100:
        raise ValueError(f"percentage must be 0-100, got {value}")
    return value

Where validation belongs

The strategy matters less than the location. Validate once, at the boundary, and trust the value afterwards:

user input  ─┐
file data   ─┼─► validate here ─► clean values ─► the rest of the program trusts them
argv        ─┘

Re-checking the same value in every function that touches it doubles the code and the number of places a message can disagree with reality. If parse_percentage guarantees 0–100, then grade_for(percentage) does not need to check again.

A reusable prompt helper

Validation at the boundary is repetitive enough to be worth one function you keep. This one combines a retry loop, a conversion attempt, and a range guard:

def read_int(prompt, minimum=None, maximum=None):
    """Prompt until the user enters a whole number within the given bounds."""
    while True:
        text = input(prompt).strip()
        try:
            value = int(text)
        except ValueError:
            print(f"  '{text}' is not a whole number.")
            continue
        if minimum is not None and value < minimum:
            print(f"  must be at least {minimum}.")
            continue
        if maximum is not None and value > maximum:
            print(f"  must be at most {maximum}.")
            continue
        return value

age = read_int("Age: ", minimum=0, maximum=120)
sides = read_int("Number of dice: ", minimum=1)

Note what it does not do: it never raises. This function's whole job is to deal with a human at a keyboard, where the right response to bad input is to ask again. It is the place where "handle it" belongs, which is why every function behind it can simply assume a valid integer.

Two kinds of function, two kinds of error handling

Interactive functions talk to a user and should loop and re-prompt. Computational functions take values and return values; they should raise and let the caller decide. Keeping these separate — no input() inside a calculation, no re-prompting inside a parser — is what makes code testable: you can call parse_percentage("101") in a test, but you cannot test a function that stops and waits for someone to type.
